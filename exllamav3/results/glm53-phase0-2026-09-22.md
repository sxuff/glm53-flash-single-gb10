# GLM-5.3 GB10 Phase 0 decision report

Date: 2026-09-22

## Decision

The patched SGLang/EXL3 deployment is correct and remains useful as a 262K-context specialty lane, but it should not be the primary low-latency runtime. The performance problem is the SGLang EXL3 adapter/runtime path, not the 2.05-bpw checkpoint itself.

Native fused-linear engineering is technically justified only if SGLang's 262K context, multimodal API, or serving features are required. It is not the cheapest path to a faster primary endpoint because exllamav3 already demonstrates 23.97 tok/s on the same checkpoint, while the existing llama.cpp GGUF lane reaches 29.30 tok/s with DFlash2.

## Matched four-workload measurements

All llama.cpp arms used the same Unsloth UD-IQ2_XXS target, four fixed workloads, 400 generated tokens per workload, one warm-up and one measured request, temperature 0, one slot, 8K context, and zero swap growth.

- SGLang + EXL3 2.05 bpw, no speculation: 11.63 mean decode tok/s. Aggregate wall rate 11.15 tok/s.
- llama.cpp UD-IQ2_XXS, no speculation: 18.19 mean server decode tok/s. Aggregate wall rate 17.95 tok/s.
- llama.cpp UD-IQ2_XXS, native MTP n=2: 27.17 mean server decode tok/s. Aggregate wall rate 26.13 tok/s. Draft acceptance 70.11%.
- llama.cpp UD-IQ2_XXS, DFlash2 Q4_K_M n=3, p_min 0.30: 29.30 mean server decode tok/s. Aggregate wall rate 27.47 tok/s. Draft acceptance 63.91%.

Relative to SGLang:

- llama.cpp no-spec: 1.56x
- llama.cpp native MTP: 2.34x
- llama.cpp DFlash2: 2.52x

## Same-checkpoint runtime diagnostic

The installed exllamav3 runtime initially failed on GB10 because its vendored KDA Triton kernel called `triton.next_power_of_2()` from inside the JIT kernel. A local compatibility image moved the host-side calculation into a constexpr launch argument.

With that compatibility patch:

- exllamav3, same EXL3 2.05-bpw checkpoint, no speculation: 23.97 median decode tok/s over three 512-token requests.
- Median wall rate: 23.66 tok/s.
- Median TTFT: 0.357 seconds.
- MemAvailable after load and generation: 33.53 GB.
- Host swap decreased slightly; no growth occurred.
- This is 2.06x SGLang on the same checkpoint and 1.32x llama.cpp no-spec on the different GGUF artifact.

The exllamav3 output was coherent under the model's chat template, but three greedy runs were not byte-identical. It is therefore a performance and architecture diagnostic, not yet a production-quality replacement.

Exllamav3 MTP n=2 loaded only after shrinking the cache to 1,024 tokens and recurrent cache to 1 GiB. It measured 24.03 tok/s, essentially no improvement, with 39.10% draft acceptance. It is not worth promoting in this form.

## Byte ledger

The SGLang loader's own end-of-load receipt reports:

- Text-path dense modules dequantized to BF16: 9.043 GB resident.
- Of that, `self_attn.qkv_proj`: 6.845 GB.
- Vision-only BF16 fallback: 0.570 GB.
- Native dense trellis: 1.860 GB.
- Native expert trellis bank: 76.548 GB.
- Routed experts: 288 total, top-8 active. Estimated active expert bytes per token: 2.126 GB.
- BF16 passthrough tensors: 2.333 GB resident, not all necessarily read per token.

The plausible short-context read envelope is approximately 13.0 to 15.4 GB per token. At 11.63 tok/s, that corresponds to roughly 151 to 179 GB/s effective bandwidth. This is consistent with bandwidth-bound decode.

Removing the text-path BF16 fallback is therefore the highest-value SGLang engineering target. Native QKV alone removes most of the avoidable per-token traffic.

## Nsight result

Nsight Systems was attempted twice through the image's bundled CLI. Its profiler overhead consumed enough unified memory that SGLang could not allocate even one hybrid KDA/Mamba request-state slot. The second attempt reduced context to 64K, disabled multimodal serving, captured only batch-size-one decode graphs, and lowered the static memory fraction. It still failed during hybrid-state pool allocation.

No kernel-time percentages are claimed. The profiling failure itself confirms that this 128 GB deployment has insufficient headroom for Nsight plus the current BF16-heavy SGLang representation.

## Engineering recommendation

If SGLang must be retained:

1. Implement native per-shard QKV execution with private graph scratch for every concurrent projection.
2. Re-run the 30/30 stream-safety harness and extend it to every newly native fused module and captured batch size.
3. Require per-module numerical parity against exllamav3 at m=1 through m=8.
4. Then move shared-expert gate/up and fused q/kv-a projections off the BF16 fallback.
5. Retest MTP only after native fused linears recover memory headroom. Current MTP acceptance and speed are not sufficient.

Expected outcome from measured evidence:

- SGLang configuration tuning alone: approximately 11.5 to 12.5 tok/s.
- SGLang native fused-linears: worth prototyping, but any 16 to 24 tok/s estimate remains a hypothesis until measured.
- exllamav3 same-checkpoint native runtime: already measured at 23.97 tok/s, but needs deterministic-output and serving-feature work.
- llama.cpp DFlash2: current measured speed winner at 29.30 tok/s.

## Restored state

The persistent patched SGLang service and its authenticated bridge and Tailscale proxy were restored after the experiments. A bearer-authenticated external canary returned model `glm53-flash-exl3-2p05-pr2`, `finish_reason=stop`, and `ANSWER: 54` for 9 × 6.
